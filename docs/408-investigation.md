# 408 与登录续期排查记录

## 已确认的现象

2026 年 10 月 22 日的服务记录中，两个生成请求在提交任务阶段分别用时 496 毫秒、588 毫秒，均收到 HTTP 408，响应为 `{"error_code":"timeout_error","message":"system under load"}`。余额请求正常返回 HTTP 200，未收到可供轮询的任务链接。

这些响应证明错误由上游返回，不能证明是账号到期、额度耗尽或本服务生成超时；也不能仅凭错误文本判断是限流、供应商拥堵或登录验证问题。

当前部署版本曾存在以下处理：收到 `system under load` 后不等待正常续期周期，清空风险会话及对应 Cookie，转而启动浏览器；浏览器失败后将账号标为已过期。这个后续状态不能作为先前 408 的根因证据。

## 修复内容

- 保留正常续期周期，生成繁忙不触发清空会话。
- 原样传递浏览器签发的风险会话，不按其中的标记删除供应商字段。
- 管理入口、定时续期和浏览器使用一致的 150 秒期限，避免外层 90 秒中断内层等待。
- 增加会话原值传递和页面加载较慢时的回归校验。

## REA 证据及限制

使用 REA 6.5.0 的 `inspect_web_network_capture` 分析服务脱敏日志生成的 HAR 副本，证据编号为 `ev_cca7e2983ca5753175271ad62a6ddb041d47e1f9b2901b7b8da440bfd96eb77c`。

分析副本共 6 条请求，来自两次失败调用。它不是浏览器原始抓包，缺少真实 HTTP 版本及每个上游请求的独立开始时间；HAR 中的等待时间来自服务记录的总时长。REA 没有访问记录中的 URL，也不能由此确定上游内部拒绝原因。

本次改动修复已确认的客户端会话处理问题，不把上游 408 直接改为成功，也不自动重放可能重复计费的生成请求。是否恢复生成须以部署后的实际结果为准。
